8. Verification, payments, finance, analytics, audit, admin security

These modules turn a sign-up into a paying professional and give the team the tools to run the service: checking diplomas, taking payments, counting money, measuring use without spying, keeping an unchangeable log of every admin action, and protecting the console itself.

8.1 Verification

A person proves two things, in separate cases: their identity (national ID, passport, or student card for students) and their status — enrolment for a student (STUDENT_STATUS), residency or the Ordre des médecins for a resident or doctor (PROFESSIONAL_STATUS).

On the reviewer's side (VerificationReviewService), a reviewer claims a case (so two people never decide the same one), views documents in a restricted viewer (60-second signed URLs, a watermark with the reviewer's name, every view audited), then approves or rejects with a reason code. Approval copies the proven role and details to the profile and schedules the documents' deletion: files are kept only as long as the retention rule says.

8.2 Billing: plans, checkout, gateways

Plans are versioned: the Super Admin publishes a plan version with its price, duration and « inclus / non inclus » lines; a price change is a new version, and running subscriptions keep theirs. Checkout is open only to an active, professionally verified doctor or resident (students never pay; nobody pays before verification — ADR-006 Q6).

8.3 Finance

Finance reads transactions (it never changes them) and adds what the business needs around them: payment fees (estimated from a rate per gateway × card, later replaced by the provider's statement), operating expenses (voided, never deleted), exceptional adjustments (two admins) and CSV reports. 8.4 Analytics without spying

[[code apps/api/src/modules/analytics/analytics.service.ts | export class AnalyticsService | 10]]

The app sends only event names with counts, codes and flags. The server adds the envelope from its own facts: a keyed hash of the person (stable, not reversible), tier, profession, specialty, wilaya. Each event type has a strict schema; anything else is dropped. Dashboards hide any cell behind fewer than 10 people (« < 10 »).

8.5 The audit log

[[code apps/api/src/modules/audit/audit.service.ts | export class AuditService | block]]

Every admin change calls audit.record({...}) with who, what, which record, before/after and the reason the admin typed. The database table itself refuses UPDATE and DELETE, so even a bug cannot rewrite history.

Grants are given per admin, from presets (Super Admin, Verification reviewer, Library manager, Calculator editor, Clinical reviewer…) adjustable one by one; a grant can also be temporary (a few hours). Separation of duties is checked both in Admin Web (live, before saving) and by the API.

8.7 The admin module

modules/admin holds read-only screens that combine several modules: « Vue d'ensemble » (the ledger strip and work lists), « Utilisateurs » (search and the user drawer: profile, access with its inputs, subscriptions, activity counts), and the audit log with its CSV export.
