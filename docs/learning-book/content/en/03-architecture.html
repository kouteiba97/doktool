3. The architecture in one chapter

Before reading modules one by one, it helps to follow one request from the phone to the database and back, and to know the handful of mechanisms every feature reuses: tokens, the access decision, the error envelope, file storage, background jobs, messages and offline copies.

3.1 The life of one request

Take the doctor opening a prescription model on the phone. This is what happens, file by file:

PHONE API DATABASE / R2 reference_viewer_screen.dart └ openedReferenceProvider └ ReferenceFiles.download(id) └ generated client GET /v1/reference-documents/{id}/file-url └ AuthInterceptor adds "Authorization: Bearer <access token>" ─────────► ViewerAuthGuard: token valid? session live? ReferenceLibraryController.fileUrl() └ ReferenceDocumentsService.fileUrl() reads the published row ──► PostgreSQL └ AccessService.decideItems() policy evaluated again: AVAILABLE or LOCKED? └ StorageService.getSignedReadUrl() 10-minute signed URL ◄───────── { url, sha256, … } (or { error: { code: "FEATURE_LOCKED" … } }) └ dio GET signed url (no token) ───────────────────────────────────────────────────────► R2 bucket └ SHA-256 of the bytes == published sha256 ? else refuse to show └ pdfrx draws the pages (no download, print or share button)

Three ideas are visible in this one example and repeat everywhere:

  1. The guard proves who is calling (a user token, a demo token or an admin cookie).
  2. The access policy decides what they may do, again, on this exact request.
  3. Files never pass through the API: it hands out a short signed URL, and the client checks the file's fingerprint.

3.3 The access decision

Access is computed, never stored. AccessService.profileFor(viewer) gathers three facts — the account (status, professional type), the verification cases and the current subscription — and gives them to a pure function, evaluateAccess, together with the policy table. Chapter 6 reads that table line by line. What matters here: every content endpoint calls it, and the mobile app receives the result from GET /v1/me/access only to draw locks.

3.4 One error format for everything

Every refusal is a DomainError with a stable code (FEATURE_LOCKED, OTP_INVALID, SESSION_INVALID…). The global ErrorFilter turns any exception into the same JSON:

HTTP 403 { "error": { "code": "FEATURE_LOCKED", "message": "for developers only", "details": { "lockReason": "…" } } }

The apps never show message; they translate code with their own catalogue (mobile ApiError + commonErrorText, admin useErrorText).

3.5 Files: R2, signed URLs and upload intents

All files (reference PDFs, profile photos, verification documents, recovery photos) are in Cloudflare R2, reached only through StorageService. Two buckets exist: doktool-content (reference PDFs, photos) and doktool-private (identity documents). Nothing is public. Uploads follow the same three steps everywhere:

  1. The client declares the file (purpose, size, type, SHA-256). The API records an upload intent and answers with a signed PUT URL valid 15 minutes.
  2. The client sends the bytes straight to R2.
  3. The client confirms; the API checks size, type and the first bytes' signature (a PDF must start with %PDF), then attaches the file to its record.

3.7 Messages to people

Codes and security notices go out by e-mail (SMTP) or SMS (Infobip or Twilio, with a fallback, ADR-022) through MessageDelivery. Their texts come from server catalogue keys (server.security.…) in the account's language. In-app notifications are rows of the notifications table holding a catalogue key and parameters — never free text.

3.8 Offline

Every real account (students included) can keep, on the phone, the reference PDFs it may open, the published calculator versions and the pregnancy profiles it opened. The API publishes an offline manifest (GET /v1/offline/manifest): what this person may keep, with a version and a SHA-256 for each item. The app's OfflineSyncController downloads what is missing or changed, deletes the rest, and always shows the data version and whether what you see is live or cached.

3.9 How modules are allowed to depend on each other

Modular monolith (ADR-001). One server, but each module owns its tables. Another module may use it only through what its index.ts exports — usually a service with a few read methods. That is why, for example, AccessService asks UsersService.getAccessFacts() instead of reading the users table itself. A unit test checks that every Prisma model sits in the section of the module that owns it.
