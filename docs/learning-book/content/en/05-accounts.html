5. Accounts: sign-up, sign-in, sessions, recovery, deletion

Two modules hold accounts. users owns the account rows (names, contacts, professional profile, preferences). auth owns everything that proves who someone is: codes, passwords, sessions, refresh tokens, contact changes, recovery and deletion (ADR-009, ADR-023).

5.1 One field for e-mail or phone

People sign up with an e-mail or an Algerian mobile number, typed in the same field. Everything starts by normalising it:

5.3 One-time codes

OtpService serves four purposes: sign-up, password reset, contact change and account recovery. Its rules: 6 digits; the code itself is never stored (only an HMAC bound to the challenge); 60 seconds between sends and at most 5 sends; 3 wrong codes lock the challenge for 10 minutes; a challenge can only be consumed for its own purpose.

[[code apps/api/src/modules/auth/otp.service.ts | private async verify( | block]]
No account enumeration. « Mot de passe oublié » always answers with a challenge, even for an identifier with no account — in that case nothing is sent (delivers()), but the answer looks identical, so nobody can test which e-mails have an account.

5.4 Sign-in, lockout and sessions

[[code apps/api/src/modules/auth/auth.service.ts | async signIn( | block]]

Read it as a checklist: a rate limit per IP and per identifier; five wrong passwords lock the account for 15 minutes (ACCOUNT_LOCKED with retryAt); suspended and unconfirmed accounts are refused with their own codes; a success opens a session bound to the device's installation id and — important for recovery — cancels any account recovery someone else started.

A session is a row of user_sessions with its refresh tokens in refresh_tokens (only their SHA-256). The API can list a person's sessions (GET /v1/me/sessions) and end one (DELETE /v1/me/sessions/:sessionId); the V1 app does not show this list yet, but a password change, a recovery or a suspension use the same revocation. Because UserTokens.verify checks the session on every request, the other device is out at its very next call.

5.5 Changing contacts and password

AccountSecurityService (Settings › « Sécurité du compte ») follows one principle: every change asks for the current password, so a borrowed unlocked phone cannot take over the account; and every change is announced on the other contact, so the owner learns about it even if the attacker controls one channel.

5.6 Assisted recovery: « J'ai perdu l'accès aux deux »

When someone has lost both their e-mail and their phone, a human checks their identity:

[[code apps/api/src/modules/auth/account-recovery.service.ts | export class AccountRecoveryService | 24]]
1 start lost contact + first/last name + NEW contact → code sent to the new contact 2 confirm code proves the new contact → recovery token (60 min to finish) 3 photos identity document + selfie → private bucket (JPEG/PNG, 10 MB, signed upload) 4 submit request goes to Admin Web « Récupération » answer promised within 72 h 5 review admin compares photos with the verified identity → approve (note) or reject (reason) 6 hold 24 h the owner is told; signing in with the password CANCELS the request 7 apply job every 10 min: new contact replaces the old ones, password unusable, all devices out

The apply step is where the October 2026 audit found a race: the request is now claimed first (APPROVED → APPLIED in one conditional update), and only then are the contacts replaced. If the owner cancels at the same instant, the claim fails and nothing changes.

5.7 Deleting an account

[[code apps/api/src/modules/auth/account-deletion.service.ts | async delete(userId | block]]

Each module that holds personal data exposes an eraseUser(userId) method; deletion calls them all, anonymises the account row (finance and the audit log must keep their history, without a name), revokes every session and writes one audit entry. On the phone, the app then forgets every personal setting it kept (chapter 11).
