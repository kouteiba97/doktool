14. Working on the code: tests, CI and recipes

You now know where everything is. This last chapter is practical: how to check your work, and the exact steps for the changes you will make most often.

14.1 Before every commit

DATABASE_URL=postgresql://…/doktool_test npm run ci # format, lint, types, i18n, tokens, contract, all tests cd apps/mobile && flutter analyze && flutter test npm run build -w @doktool/admin # when Admin Web changed
Use a dedicated test database. Integration tests do not roll back. A test that changes something platform-wide (for example the double sign-off policy) must put it back, as clinical-review.e2e.spec.ts does.

14.2 Recipe: add an API endpoint

  1. Write the service method in the module that owns the data (with a one-line comment).
  2. Add the DTO classes (@ApiProperty + class-validator decorators).
  3. Add the controller method with the right guard: UserAuthGuard, ViewerAuthGuard, @RequireFeature or @RequireGrants. Admin changes call AuditService.record with the reason.
  4. Write an integration test in apps/api/test/integration.
  5. Regenerate the contract and both clients:
npm run openapi:generate -w @doktool/api npm run generate:api -w @doktool/admin cd apps/mobile && dart run swagger_parser && dart run build_runner build --delete-conflicting-outputs

14.3 Recipe: add a column or a table

  1. Edit apps/api/prisma/schema.prisma in the section of the owning module (// ── [module] ──); a unit test checks table ownership.
  2. Write the migration by hand in prisma/migrations/<timestamp>_<name>/migration.sql. An enum ADD VALUE goes in its own migration.
  3. Indexes written in SQL (trigram, partial) are also declared in the schema, or prisma migrate diff will propose to drop them. Check with npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code.
  4. npm run prisma:migrate:deploy -w @doktool/api, then prisma generate runs on install.

14.4 Recipe: add or change a text

// keys.json { "fr": { "mobile.home.newKey": "Bonjour" }, "en": { "mobile.home.newKey": "Hello" }, "remove": [] } npm run add-keys -w @doktool/i18n -- keys.json npm run build:arb -w @doktool/i18n cd apps/mobile && flutter gen-l10n

Admin Web reads the catalogue directly; mobile uses AppLocalizations.of(context).homeNewKey. CI fails if a key exists in one language only.

14.5 Recipe: add a mobile screen

  1. Create the screen in lib/src/features/<feature>/, built from lib/src/ui widgets and tokens only.
  2. Add its path to Routes and a GoRoute in app_router.dart; if it is for real accounts only, add it to Routes.accountOnly.
  3. Load data through a provider; draw loading (skeleton), error (« Réessayer ») and empty states.
  4. Locked things stay visible: use the AccessProfile, LockLabel and showLockSheet.
  5. Add a widget test, and the screen to accessibility_test.dart.
  6. Format with dart format --page-width 120 (never on doktool_tokens.dart).

14.6 Recipe: add an Admin Web section

  1. The API endpoints with @RequireGrants; a new grant goes in grants.ts and its label in features/permissions/grants.ts (the build fails until it is labelled).
  2. src/features/<section>/: the page, its drawers and dialogs, labels.ts for status names and tones.
  3. src/app/admin/<section>/page.tsx wrapping it in <RequireGrant>, and a link in shell/nav.ts.
  4. Every change asks for a reason (ReasonDialog) and shows a toast on success.

14.7 Adding a calculator is not a code change

A new calculator is data, entered in Admin Web by a doctor from a cited source (chapter 13.5), reviewed by someone else, and published. No deployment is needed: phones receive it at their next list or sync. The engines change only when a new kind of operator or input is needed — then both engines, checkDefinition, the shared vectors and the version number of the engine change together.

14.9 What the October 2026 audit changed

The full report is docs/CODE-AUDIT-2026-10.md. In short: eighteen defects fixed with tests (the most serious: re-verification dropping a paying doctor's access, and a race in account recovery), performance of the offline manifest and favorites improved about tenfold, comments added to every function and button of the three apps, and six recommendations recorded for decisions that need the Product Owner or a real R2 bucket.

14.10 Rebuilding this book

python3 docs/learning-book/build.py # HTML + PDF, English and Arabic (needs Chrome) python3 docs/learning-book/build.py --html # HTML only

Chapters are in docs/learning-book/content/en and content/ar; folder introductions in folders.json. Code excerpts and Appendix A are read from the sources at build time, so after a code change, rebuilding is enough to bring the book up to date. A placeholder whose anchor no longer exists stops the build with its name, so nothing goes silently stale.
