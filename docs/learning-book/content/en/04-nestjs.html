4. How the API is built — NestJS, using DokTool's own code

NestJS is a framework that organises a Node.js server into modules, each made of controllers (HTTP endpoints), services (the logic) and DTOs (the shapes of what comes in and goes out). Nest builds every object and hands it what it needs through its constructor — dependency injection. This chapter teaches those pieces with the smallest complete module of DokTool: notifications.

4.4 A controller: endpoints and guards

A controller maps URLs to methods. Decorators (the @… lines) tell Nest the HTTP verb, the guard to run first, and tell Swagger how to document the endpoint:

[[code apps/api/src/modules/notifications/notifications.controller.ts | @ApiTags('notifications') | block]]
  • @Controller(`${USER_API_PREFIX}/me/notifications`) — every route here starts with /v1/me/notifications.
  • @UseGuards(UserAuthGuard) — a valid user token is required (a demo token is not enough: demos have no notifications).
  • @CurrentUser() user — injects the principal the guard stored on the request (userId, sessionId).
  • @Query() query: NotificationListQuery — the query string, validated against the DTO class.
  • @Param('id', new ParseUUIDPipe()) — the URL id, refused unless it is a UUID.
  • @HttpCode(HttpStatus.NO_CONTENT) — answers 204 with no body.
Controllers stay thin. In DokTool a controller only translates HTTP into a service call and the service's result into a DTO. Every rule lives in services, so it can be tested and reused.

4.5 DTOs: the contract

A DTO is a class with decorated fields. class-validator decorators (@IsOptional, @IsISO8601…) check incoming data; @ApiProperty describes the field in the OpenAPI contract, from which the mobile and admin clients are generated. Changing a DTO therefore changes both apps' generated code.

[[code apps/api/src/modules/notifications/notifications.dto.ts | export class NotificationDto | block]]

The static from() turns an internal record into exactly what the client may see (dates as ISO text, parameters as strings).

4.9 How the API is tested

  • Unit tests (apps/api/test/unit): pure logic without a database — the access policy matrix, the calculator engine, CSV cells, payment gateway parsing, search ranking.
  • Integration tests (apps/api/test/integration/*.e2e.spec.ts): the real application (configureApp included) against a real PostgreSQL test database, driven over HTTP with supertest. Helpers in actors.ts create a doctor, a student, an admin with given grants…, and content.ts publishes test content.
