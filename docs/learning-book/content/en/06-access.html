6. Access: who may open what

This is the most important chapter for understanding DokTool's behaviour. One table decides what each kind of person can open; one pure function applies it; every endpoint re-checks it; the apps only draw the answer. If you understand modules/access, you understand why a screen shows a lock, an explanation or a « Voir les offres » button.

6.1 The inputs

For a demo session, the only input is "this is a demo" (and which profession it previews). For a real account, AccessService gathers three facts in parallel, each from the module that owns it:

The content rules use three scopes: ALL (everything opens), STUDENT_TIER (items marked for students, plus samples), DEMO_SAMPLE (only items flagged demoSample), and NONE for a restricted account. A locked item always carries its lockReason and, when one exists, its unlockPath — the single screen that can help (sign up, see plans, start verification…). Students get explanations without an unlock path: no upsell (Lock L38).

6.4 Re-verification never interrupts access

A verification expires (professional status after a set period; see chapter 8). Renewing it opens a new case of the same type. Before the October 2026 audit, the newest case — still undecided — replaced the verified one, and a paying doctor fell to PROFESSIONAL_UNPAID the moment they tapped « Renouveler ». accessSnapshot now keeps the earlier decision counting while the new case is undecided, and flags renewalPending so purchase shows « vérification en cours »:

6.6 Re-checking on every endpoint

Two mechanisms enforce the profile on the server:

  • @RequireFeature('…') on a route (chapter 4.7) refuses a locked feature before the handler runs.
  • Content services call AccessService.decideItems(viewer, items) and only return a PDF URL, a calculator definition or a profile's content when the item is AVAILABLE; a locked item is still listed, with its lock.

6.7 Viewers: user or demo

[[code apps/api/src/infrastructure/security/viewer-auth.guard.ts | export type Viewer | 5]] [[code apps/api/src/infrastructure/security/viewer-auth.guard.ts | export class ViewerAuthGuard | block]]

Read routes accept both kinds of token; write routes (favorites, history, verification, payments) use UserAuthGuard, which refuses demo tokens. Demo and user tokens are signed with the same key but have different audiences, so one can never pass for the other.

6.8 The demo

[[code apps/api/src/modules/demo/demo.service.ts | export class DemoService | 12]] [[code apps/api/src/modules/demo/demo.service.ts | async start( | block]]

One device keeps one active demo session, identified by the phone's installation id. Nothing a demo does is written to user tables: its favorites live in the phone's memory only. When the same phone confirms a new account, markConverted closes the demo as CONVERTED, so the « Démo » analytics funnel can count conversions (another audit fix).

6.9 What the apps do with the profile

  • Mobile: AccessController loads the profile at launch, on resume and after verification or payment. Rows draw a LockLabel; tapping a locked row opens showLockSheet with the explanation and, if there is one, the single unlock action. Locks are never red.
  • Admin Web: the user drawer's « Accès » tab shows an account's profile and the inputs it came from (AccessService.explainForUser), so support can answer "why can't I open this?".
