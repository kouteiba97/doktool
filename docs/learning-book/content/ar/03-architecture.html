3. البنية في فصل واحد

قبل قراءة الوحدات واحدة واحدة، يفيدك أن تتبع طلبًا واحدًا من الهاتف إلى قاعدة البيانات ثم العودة، وأن تعرف الآليات القليلة التي تعيد كل ميزة استعمالها: الرموز، قرار الوصول، غلاف الأخطاء، تخزين الملفات، المهام الخلفية، الرسائل، والنسخ دون اتصال.

3.1 حياة طلب واحد

لنأخذ طبيبًا يفتح نموذج وصفة على الهاتف. هذا ما يحدث، ملفًا بملف:

PHONE API DATABASE / R2 reference_viewer_screen.dart └ openedReferenceProvider └ ReferenceFiles.download(id) └ generated client GET /v1/reference-documents/{id}/file-url └ AuthInterceptor adds "Authorization: Bearer <access token>" ─────────► ViewerAuthGuard: token valid? session live? ReferenceLibraryController.fileUrl() └ ReferenceDocumentsService.fileUrl() reads the published row ──► PostgreSQL └ AccessService.decideItems() policy evaluated again: AVAILABLE or LOCKED? └ StorageService.getSignedReadUrl() 10-minute signed URL ◄───────── { url, sha256, … } (or { error: { code: "FEATURE_LOCKED" … } }) └ dio GET signed url (no token) ───────────────────────────────────────────────────────► R2 bucket └ SHA-256 of the bytes == published sha256 ? else refuse to show └ pdfrx draws the pages (no download, print or share button)

تظهر في هذا المثال الواحد ثلاث أفكار تتكرر في كل مكان:

  1. الحارس (guard) يثبت هوية المتصل (رمز مستخدم، أو رمز عرض تجريبي، أو كعكة مشرف).
  2. سياسة الوصول تقرّر ما يُسمح له به، من جديد، في هذا الطلب بالذات.
  3. الملفات لا تمر عبر الخادم أبدًا: يمنح الخادم رابطًا موقّعًا قصيرًا، ويتحقق العميل من بصمة الملف.

3.3 قرار الوصول

الوصول يُحسَب ولا يُخزَّن أبدًا. تجمع الدالة AccessService.profileFor(viewer) ثلاث حقائق — الحساب (الحالة، الصفة المهنية)، ملفات التحقق، والاشتراك الحالي — وتعطيها لـدالة نقية اسمها evaluateAccess مع جدول السياسة. الفصل 6 يقرأ هذا الجدول سطرًا سطرًا. المهم هنا: كل نقطة نهاية للمحتوى تستدعيها، وتطبيق الهاتف يتلقى النتيجة من GET /v1/me/access فقط لكي يرسم الأقفال.

3.4 صيغة واحدة للأخطاء

كل رفض هو DomainError بكود ثابت (FEATURE_LOCKED، OTP_INVALID، SESSION_INVALID…). المرشّح العام ErrorFilter يحوّل أي استثناء إلى JSON نفسه:

HTTP 403 { "error": { "code": "FEATURE_LOCKED", "message": "for developers only", "details": { "lockReason": "…" } } }

التطبيقات لا تعرض message أبدًا؛ بل تترجم code بكتالوجها الخاص (في الهاتف ApiError وcommonErrorText، وفي لوحة الإدارة useErrorText).

3.5 الملفات: R2، الروابط الموقّعة، ونوايا الرفع

كل الملفات (ملفات PDF المرجعية، صور الملف الشخصي، وثائق التحقق، صور الاسترجاع) موجودة في Cloudflare R2، ولا يُوصَل إليها إلا عبر StorageService. يوجد دلوان: doktool-content (ملفات PDF المرجعية والصور) وdoktool-private (وثائق الهوية). لا شيء عام. الرفع يتبع الخطوات الثلاث نفسها في كل مكان:

  1. يصرّح العميل بالملف (الغرض، الحجم، النوع، SHA-256). يسجّل الخادم نية رفع ويجيب برابط PUT موقّع صالح 15 دقيقة.
  2. يرسل العميل البايتات مباشرة إلى R2.
  3. يؤكّد العميل؛ فيتحقق الخادم من الحجم والنوع وتوقيع البايتات الأولى (ملف PDF يجب أن يبدأ بـ%PDF)، ثم يربط الملف بسجله.

3.7 الرسائل إلى الناس

الرموز وتنبيهات الأمان تُرسَل بالبريد الإلكتروني (SMTP) أو برسالة قصيرة (Infobip أو Twilio مع بديل احتياطي، ADR-022) عبر MessageDelivery. نصوصها تأتي من مفاتيح كتالوج الخادم (server.security.…) بلغة الحساب. الإشعارات داخل التطبيق صفوف في جدول notifications تحمل مفتاح كتالوج ومعاملات — وليس نصًا حرًا أبدًا.

3.8 العمل دون اتصال

كل حساب حقيقي (بما في ذلك الطلبة) يستطيع أن يحفظ على الهاتف ملفات PDF المرجعية التي يحق له فتحها، وإصدارات الحاسبات المنشورة، وملفات الحمل التي فتحها. ينشر الخادم بيان العمل دون اتصال (GET /v1/offline/manifest): ما يحق لهذا الشخص حفظه، مع إصدار وبصمة SHA-256 لكل عنصر. متحكم التطبيق OfflineSyncController ينزّل الناقص أو المتغيّر ويحذف الباقي، ويعرض دائمًا إصدار البيانات وهل ما تراه حيّ أم محفوظ.

3.9 كيف يُسمح للوحدات أن تعتمد على بعضها

الكتلة الواحدة المقسّمة إلى وحدات (ADR-001). خادم واحد، لكن كل وحدة تملك جداولها. لا يجوز لوحدة أخرى استعمالها إلا عبر ما يصدّره ملف index.ts الخاص بها — عادة خدمة ببضع دوال قراءة. لهذا، مثلًا، تسأل AccessService الدالة UsersService.getAccessFacts() بدل قراءة جدول المستخدمين بنفسها. اختبار وحدة يتحقق من أن كل نموذج Prisma يقع في قسم الوحدة التي تملكه.
